# Standby initialization handoff: rejected

The candidate called the existing bounded small-run handoff once after a standby worker's GUC prelude. It kept the 16-worker pool and retained-worker task path intact. Live allocations remained valid while unused slots became available to other threads. The tested patch is archived; runtime source has been restored to the retained implementation.

Five allocator tests, two worker-retirement tests and the locked release build passed. A diagnostic pair observed all 16 standby threads throughout. Each engine completed three parallel heap index builds on 500,000 rows, with two pooled warm-worker claims per build and identical independently expected ordered hashes. Normal shutdown, no remaining processes and no OOM/swap were verified. Eight Bind/portal protocol groups and 192 committed updates per engine matched native PostgreSQL. These checks do not establish production readiness.

A single diagnostic startup sample showed PSS about 33 MiB lower and checked-out small-run capacity about 20 MiB lower. This is attribution evidence, not a repeated performance result. The subsequent medium comparison has five alternating repetitions per engine, one million facts, six ordinary clients, 2 GiB/no swap, separate server/client CPUs, Hearth, no tuning flags, and the unchanged 19-statement mixed bundle. All 15 trials pass correctness, restart, cleanup and timed resource-validity checks.

Against the interleaved retained Rust control, median charged peak memory falls 5.53% and process PSS 4.91%, but CPU per bundle rises 3.29%, read p99 4.40%, update p99 3.61%, aggregate p99 3.86%, range p99 8.87%, and bundle p99 3.48%. Range p99 exceeds the predeclared 5% preservation guard. The candidate is not selected, and no capacity campaign was run. The four PostgreSQL memory/latency targets remain open. Every trial is retained; no losing trial was removed.
